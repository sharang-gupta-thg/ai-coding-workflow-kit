One reference · from a one-line config edit to a new service

Match the effort to the task — write it clean, test it first, ship it verified

Two tools, one workflow. nWave structures work into waves and enforces TDD; Code Guardian reviews every change against 12 professional standards. This guide shows when to use each — light touch for daily config and bug work, the fuller flow for real features and greenfield builds. Three habits run through all of it: prompt for clean code, review for violations, follow TDD every time.

The 10-second rule

If the change has no behaviour to test (a config value, a version number), don't reach for nWave — make it, verify, and use Guardian only when a mistake would break something in production. Save the waves for anything with logic worth a failing test.

One-time setup

Run ./install.sh from the kit (see the README; it installs Code Guardian, the clean-code skills and nWave), restart Claude Code, then set the rigor profile so nWave defaults to lean output — right for solo iteration where token cost matters.

# lean = fast agent, RED→GREEN, no reviewer, ~40% of the tokens
/nw-rigor lean

# Or per-repo, committed so teammates inherit it
/nw-rigor lean --project

Bump to standard for shared features, thorough for high-risk work. Code Guardian is a global agent — call @code-guardian from any repo (@clean-code:code-guardian if you installed it as a plugin).

nWave is a graph, not a conveyor belt. Start at the earliest wave where you actually have uncertainty — and every feature ends DISTILL → DELIVER. Everything before DISTILL is skippable when you already know the answer.

Entered mid-flow and hit a gap?

Run the skipped wave late — it reads the artifacts already on disk and adjusts. Nothing breaks. Ask /nw-buddy "what should I do next?" if unsure where to enter.

Write clean code core · every task

The cheapest clean code is the code you never have to fix. Tell the agent your standards up front, in the prompt — don't wait for review to discover violations. Name the standards that matter for the task and set hard constraints.

Make it the default, not a prompt you remember

The loop in CLAUDE.md.template tells Claude to load the clean-code-martin and code-as-prose skills before writing any code and lists the rules it must write to. Because CLAUDE.md is read at the start of every session, every first draft is held to the standard without you asking. The preamble below is the same set of rules for a one-off request outside such a workspace.

A reusable prompt preamble

Paste this at the top of any "write me code" request when no CLAUDE.md carries the loop.

Write this following clean-code standards:
- Names reveal intent; no abbreviations (user not usr, config not cfg)
- Functions do one thing, ≤ ~20 lines, ≤ 3 params (use a value object beyond that)
- SOLID: single responsibility per class; depend on interfaces, inject deps
- Errors: validate inputs at the edge, fail fast, specific exceptions with context
- No magic numbers, no duplicated logic, no comments that just restate code
- Reads like prose: clarity over cleverness

Then walk me through the key design decisions.

Make it project-specific

Add the constraints that match where the code lands — name the architecture, the concurrency model, the layering:

@code-guardian before I write this — how should it fit?
Target: a layered service (Controller → Service → Provider).
Runs inside a parallel/concurrent path.
Where does validation vs orchestration vs the external call belong,
and what's the SOLID-clean shape before I start coding?

Ask for the design before the code

A 30-second Guardian check on where logic should live prevents the most expensive violation — a class quietly taking a second responsibility. Clean structure first, clean lines second.

What "clean" looks like in one glance

✗ Before

public List<int[]> getThem() {
  List<int[]> l = new ArrayList<>();
  for (int[] x : theList)
    if (x[0] == 4) l.add(x);
  return l;
}

✓ After

public List<Cell> getFlaggedCells() {
  List<Cell> flagged = new ArrayList<>();
  for (Cell cell : gameBoard)
    if (cell.isFlagged())
      flagged.add(cell);
  return flagged;
}

Same logic — intention-revealing names, a domain type instead of int[], and a predicate (isFlagged()) instead of a magic x[0] == 4. That's the bar for every function you ship.

Review for violations core · every task

Front-loading standards gets you 80% there; Code Guardian catches the rest. Run it as the last step before you commit or push — targeted for a single function, full-audit for a whole PR.

Quick check — one function, mid-work

@code-guardian Quick clean-code review of OrderValidator#validate.
Naming, single-responsibility, error handling, edge cases.

Full PR audit — the one you never skip

@code-guardian Full PR review of this branch vs main.
Cover: SOLID, input validation at the edges, error handling,
thread-safety in concurrent paths, N+1 / extra round-trips,
security, and test coverage of every case.

Rhythm

Guardian at design time (catch structural problems cheaply) and again as a full PR audit before push. For config edits and dep bumps, only when a mistake is costly. Point it at a branch, a file, or a function — it reads the code and runs git diff itself, so there is nothing to paste.

TDD in everything core · every task with logic

nWave's DELIVER wave enforces a 3-phase cycle — RED → GREEN → COMMIT — and its execution monitor keeps steps from skipping ahead. You get the same discipline by hand on any change: write the failing test first, make it pass with the minimum, commit one behaviour at a time.

RED — failing test→ GREEN — minimum to pass→ COMMIT — one behaviour
R

RED — write the test, watch it fail

Start from the acceptance criteria (or the bug report). The test must fail for the right reason before you write any implementation.

# run one focused test (syntax varies by stack — Maven shown)
mvn test -Dtest=OrderValidatorTest#rejectsNegativeQuantity
# ✗ fails — no implementation yet. Good.
G

GREEN — minimum code to pass

Write the least code that makes the test green. No gold-plating — extra behaviour needs its own test first.

mvn test -Dtest=OrderValidatorTest#rejectsNegativeQuantity
# ✓ passes
C

COMMIT — one behaviour, then the full net

mvn clean verify              # unit + integration
git commit -m "feat: reject negative order quantity"

One behaviour per commit keeps git history a readable trace of the TDD progression — exactly what nWave produces automatically in DELIVER.

Letting nWave drive the cycle

For feature work, /nw-deliver runs the whole loop: it builds a roadmap (one step per acceptance scenario) and executes each through RED→GREEN→COMMIT with monitoring. To run a single unit by hand — no full orchestration:

/nw-execute @software-crafter "reject negative order quantity"
/nw-refactor          # tidy while green
/nw-review @software-crafter task "reject negative order quantity"

How TDD folds into each scenario below

  • Bug fix — the failing test is the reproduction; it becomes your regression net.
  • New / changed endpoint — DISTILL writes the acceptance tests; DELIVER makes them pass one at a time.
  • Refactor — the special case: tests are already green and must stay green through every step.
  • Config / dep bump — no new behaviour, so no new test; the existing suite is the safety check.

Config / infra change common

Environment values, deploy settings, feature flags, connection strings, scaling. High-frequency, low-lines, usually no behaviour to unit-test. nWave adds nothing here — the value is a careful eye on blast radius.

edit config→ diff→ Guardian (if risky)→ deploy + watch metrics No waves, no TDD — there's no behaviour to test. Deliberately outside the pipeline.
1

Make the change, read your own diff

git diff -- # right environment? right target? no plaintext secret?
G

Guardian — only when a mistake takes a service down

Networking, connection routing, and secrets are where outages come from. Plain value bump → skip. Anything touching reachability → ask:

@code-guardian Review the uncommitted config change for blast radius.
Flag anything that breaks service-to-service reachability, leaks a
secret, or differs between environments.
2

Deploy and watch the signal

Trust the metrics after rollout, not the config file. Watch error rate and reachability.

✓ config in, deploy green, metrics steady

Don't over-tool this

A one-line value change needs no wave, roadmap, or test. The failure mode here is ceremony, not under-process.

New endpoint / feature the disciplined work

Where nWave earns its keep — the multi-file, test-backed changes. You know the system, so skip DISCOVER/DIVERGE and start at DISCUSS.

DISCUSS→DESIGN→DISTILL→DELIVER Skip DESIGN if it lands entirely inside existing layers with no new boundary or ADR.
1

DISCUSS — nail the contract

/nw-discuss "Add an endpoint to verify a user's email"

Request/response shape, validation rules, error cases, acceptance criteria — before touching code.

→ docs/feature/<id>/discuss/ — user stories + acceptance criteria
2

DESIGN — fit the layers (write-clean starts here)

# ground yourself in the existing structure first
/nw-design "email-verification"

@code-guardian Where should validation vs orchestration live?
Any SOLID concern? Thread-safety if it runs in a concurrent path?
3

DISTILL — acceptance tests define done (RED)

/nw-distill "email-verification"

Given-When-Then for happy path + every rejection case. These become your integration-test targets and the failing tests DELIVER drives green.

→ acceptance-tests.feature
4

DELIVER — Outside-In TDD, one commit per step (GREEN → COMMIT)

git checkout -b feature/email-verification
/nw-deliver "email-verification"
mvn clean verify

Features ship with their integration tests — a real feature is a multi-file change (endpoint model, validation, service logic, and its tests). That's the bar.

G

Guardian — full PR audit before push

@code-guardian Full PR review of this branch vs main.
Input validation at the edge, error responses & status codes,
thread-safety in concurrent paths, N+1 / extra round-trips,
test coverage of every reject case.
✓ feature merged with integration tests and a clean audit

Change an existing endpoint

Adding a field, tweaking behaviour, extending a flow. You know the area — start at DESIGN, and lead with backward compatibility because other services depend on this contract.

DESIGN→DISTILL→DELIVER
1

Check who depends on it

grep -r "the-endpoint-path" --include=*.java
# plus the OpenAPI/Swagger surface — other services consume these
G

Guardian — is the change backward-compatible?

@code-guardian Endpoint change review.
Adding optional field 'preferredLanguage' to POST /users.
Confirm: new field optional, existing callers unaffected,
response additive-only, no status-code changes.

Never remove or retype a field

Add optional, keep old behaviour, deprecate later. A breaking response change ripples into every consumer.

2

Test both paths, then implement (RED → GREEN)

/nw-distill "add-preferred-language"   # new + unchanged-caller scenarios
/nw-deliver "add-preferred-language"

✓ endpoint extended, old clients unbroken, tests prove both

Semi-greenfield big new module

A substantial new subsystem inside an existing repo — a new pipeline, a whole domain area. New boundaries and design uncertainty, but the platform, deploy, and conventions already exist. Start at DISCUSS, add DEVOPS because you're introducing new infra surface, bump rigor to standard for a reviewer.

Clean-code standards

The 12 standards Code Guardian carries. Name the relevant ones in your write / review prompts.

StandardCore idea
Clean Code (Martin)Intention-revealing names, functions do one thing, no magic numbers, comments explain why
Code as Prose (Booch)Clarity over cleverness; reads top-to-bottom like well-written prose
SOLIDSingle responsibility, open/closed, Liskov, interface segregation, dependency inversion
Defensive programmingValidate at boundaries, fail fast, assert invariants, defensive copies
ConcurrencySynchronize shared state, no races, no deadlocks
Error handlingSpecific exceptions with context, ARM/try-finally, no swallowed errors
Testing pyramidMany unit, some integration, few E2E; isolated, meaningful assertions
API designREST conventions, correct status codes, backward compatibility
Database patternsKill N+1, index right, transaction safety, connection pooling
ObservabilityStructured logs, trace-ID propagation, no PII/secrets in logs
Code reviewConstructive, specific, scoped feedback
RefactoringRPP L1–L6, behaviour preserved, tests green each step

The whole thing in one breath

Match the tool to the task. Write it clean by naming standards up front; test it first with RED→GREEN→COMMIT; review it with a Guardian audit of the branch plus /code-review for bugs. Config & bumps: just do it, Guardian if it's dangerous. Bugs: /nw-bugfix, keep the regression test. Features: DISCUSS→DESIGN→DISTILL→DELIVER on lean, ship with tests. Big module: add DEVOPS on standard rigor. New service: the full seven waves. Always end DISTILL→DELIVER; always let the metrics and the test suite have the last word.
